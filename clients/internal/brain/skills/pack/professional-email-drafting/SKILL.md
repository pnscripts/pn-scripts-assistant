# Professional email drafting

A good work email can be understood from the subject and the first two lines. Draft it; never send it on the user's behalf without explicit approval.

## Steps
1. **Collect the essentials.** Recipient and relationship, purpose, the one thing you want them to do, deadline, facts to include (dates, amounts, references), attachments, and the tone (formal, neutral, friendly). If replying, read the whole thread first.
2. **Write the subject line.** Specific and actionable, ideally with the ask or the key fact:
   - "Approval needed by Thu - Q3 training budget"
   - "Invoice 2026-114 - payment reminder"
   - "Intro - Ana (designer) and Ivo (print supplier)"
3. **Open with purpose.** Greeting, then the reason in one sentence. Skip "I hope this email finds you well" unless the relationship calls for warmth.
4. **Body: one topic, short paragraphs.** Context only as much as the reader needs. Use a numbered list for several questions so they can answer point by point.
5. **Make the ask explicit.** Who does what by when: "Could you confirm the date by Friday 12:00?"
6. **Close.** Offer help or the next step, sign off to match the tone (Best regards / Kind regards / Thanks), name and role. Add contact details only if the reader needs them.
7. **Check before handing over:** names spelled right, correct recipients and CC, attachments mentioned really exist, dates match weekdays, no confidential data meant for someone else, tone fits.

## Templates
**Request**
```
Subject: <Request> - <topic> by <date>
Hi <Name>,
I'm writing to ask for <thing> for <reason>.
<1-2 lines of context>
Could you <specific action> by <date/time>?
Thanks in advance,
<Name>
```
**Follow-up (no reply)**
```
Subject: Re: <original subject>
Hi <Name>, a quick follow-up on my note from <day> about <topic>.
Are you able to <action> by <new date>? If someone else handles this, I'd be grateful for their contact.
```
**Polite refusal**
```
Thank you for thinking of us for <request>. Unfortunately we can't <do X> because <short reason>.
What we can offer instead is <alternative>. 
```

## Pitfalls
- Several unrelated topics in one email; split them so each can be answered and searched.
- Burying the ask in the last paragraph.
- Reply-all to a large list when only one person needs it.
- Over-apologising or excessive hedging, which weakens the request.
- Emotional replies; when the user is upset, draft, then suggest waiting before sending.
- Inventing facts (dates, prices, promises) the user did not give; leave a clear [placeholder] instead.

## Output
Return: subject line, the full email ready to paste, and any [placeholders] the user must fill. Optionally offer a shorter or more formal variant. Remind the user to check recipients and attachments before sending.
